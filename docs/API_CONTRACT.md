# InsuraLens — API Contract

Contract for the backend engineer. The frontend already calls every endpoint below through `src/api/*.js`; in this repo each function resolves mock data from `src/mocks/` after a small delay. Replace the mock bodies with `request()` calls (every function carries a `TODO(backend):` comment with its exact endpoint) and nothing else in the UI changes.

- **Base URL**: value of `VITE_API_BASE_URL` (origin only, no trailing slash, no `/api` suffix) — see `.env.example`. Endpoints below are appended as-is.
- **Content type**: `application/json; charset=utf-8` unless noted (uploads are `multipart/form-data`).
- **Auth**: bearer token in `Authorization: Bearer <token>` once sessions exist (`src/api/http.js` sends it automatically when a token is stored). See [Open questions](#open-questions-for-backend).
- **Vocabulary**: `status`, `priority`, and `incident` values are tokens, not display text — see [Shared vocabulary](#shared-vocabulary).

## Error format

Every non-2xx response must use this envelope. `request()` in `src/api/http.js` converts it to `ApiError { status, code, message }` and the pages render `message` in their error/retry states.

```json
{
  "error": {
    "code": "invalid_credentials",
    "message": "Incorrect email or password",
    "details": null
  }
}
```

| `status` | When | Notes |
| --- | --- | --- |
| 400 | Validation failed | `details` may carry field errors |
| 401 | Missing/expired/invalid credentials | Login form maps this to "Incorrect email or password" |
| 404 | Claim / notification not found | `getClaim()` maps this to `null` (workspace shows "Claim not found") |
| 413 | Upload too large | See [Upload rules](#upload-rules) |
| 422 | Unsupported file type / business rule | `message` shown verbatim |
| 500 | Server error | Generic message OK |
| 0 (client-only) | Transport failure | `code: "network_error"` — generated by `request()`, no server involvement |

Stable `code` strings the frontend already handles: `invalid_credentials`, `network_error`. Prefer adding new codes over reusing them.

## Pagination format

`GET /api/claims` accepts optional pagination params:

| Query param | Type | Default | Meaning |
| --- | --- | --- | --- |
| `page` | integer ≥ 1 | — | 1-based page number |
| `page_size` | integer 1–100 | 25 | Rows per page |

- **Without `page`** (the mode the frontend uses today — it paginates client-side): respond with a **bare JSON array** of claims (after applying any filters).
- **With `page`**: respond with the envelope:

```json
{
  "items": [ /* Claim[] */ ],
  "page": 1,
  "page_size": 25,
  "total": 128,
  "total_pages": 6
}
```

When the backend turns on server pagination, the only frontend change is one line in `listClaims()` (`src/api/claims.js`): `return (await request('/api/claims', { query: params })).items`.

Other list params (ignored by the mock today, honored by the server): `status`, `priority`, `incident` (tokens, comma-separated for multi), `q` (search), `sort` (`id|customer|incident|date|evidence|ai|policy|priority|status|updated`), `dir` (`asc|desc`).

## Endpoints

### POST `/api/auth/login`

Sign in. Mock behavior to preserve: any well-formed email + password `demo123` succeeds; any other password → 401 `invalid_credentials`. Nothing is stored client-side today (the form deliberately does not persist credentials).

Request:

```json
{ "email": "alex.morgan@insuralens.demo", "password": "demo123" }
```

Response `200`:

```json
{
  "user": {
    "id": "usr-demo-001",
    "name": "Alex Morgan",
    "email": "alex.morgan@insuralens.demo",
    "role": "claims_reviewer"
  },
  "token": "demo-token-not-a-real-credential"
}
```

Error `401`:

```json
{ "error": { "code": "invalid_credentials", "message": "Incorrect email or password", "details": null } }
```

Afterwards the frontend will call `setToken(token)` from `src/api/http.js` (one line in `src/api/auth.js`).

### GET `/api/auth/me`

Current session's user. Response `200`: the `user` object above. Error `401` when the token is missing/expired.

### POST `/api/auth/logout`

Ends the session. Response `204` (no body). Frontend clears the stored token with `clearToken()`.

### GET `/api/dashboard/summary`

All Dashboard cards in one payload, so the page can never disagree with itself.

Query params: none (today). Future option: `?as_of=` for date scoping.

Response `200`:

```json
{
  "total": 128,
  "open": 98,
  "needsReview": 23,
  "inAnalysis": 30,
  "awaitingDecision": 44,
  "stages": {
    "new": 9,
    "evidence_collection": 11,
    "ai_analysis": 30,
    "human_review": 44,
    "completed": 30
  },
  "priorities": { "high": 23, "medium": 51, "low": 50 },
  "insights": { "damagePattern": 6, "missingEvidence": 4, "policyReview": 9 },
  "recentActivity": [
    { "time": "09:42", "action": "AI analysis completed", "claim": "CLM-10482" }
  ]
}
```

Rules: `stages` keys are exactly the five stage tokens (they must sum to `total`); `open` = all stages except `completed`; `needsReview` = `priorities.high`; `insights` predicates are described on the dashboard cards (rear-end+high, evidence missing, policy verification) — keep them consistent with the claims data the server holds.

### GET `/api/claims`

Work queue for `#/claims` and the source for `#/claims/:id`.

Query params: see [Pagination format](#pagination-format) plus `status`, `priority`, `incident`, `evidence`, `policy_match`, `q`, `sort`, `dir`.

Response `200` (no `page`): bare array.

```json
[
  {
    "id": "CLM-10482",
    "customer": "Sarah Mitchell",
    "incident": "vehicle_collision",
    "dateReported": "Oct 2, 2026",
    "dateReportedValue": 1790899200000,
    "policyRef": "POL-88214",
    "evidenceItems": 6,
    "evidence": "Complete",
    "aiAnalysis": "Available",
    "policyMatch": "Matched",
    "priority": "high",
    "status": "human_review",
    "updatedLabel": "12 min ago",
    "updatedMinutes": 12,
    "description": "Rear-ended at a traffic light; two-vehicle incident.",
    "photos": [
      { "name": "front-bumper.jpg", "url": "/uploads/CLM-10482/front-bumper.jpg", "caption": "Front bumper damage" }
    ]
  }
]
```

Field notes:

- `dateReported` is the preformatted display string the table shows; `dateReportedValue` is epoch **milliseconds** (UTC midnight of the reported date) and is what sorting/filtering should use. New claims arrive with `dateReportedValue` derivable from an `YYYY-MM-DD` date.
- `evidence` ∈ `Complete | Incomplete`; `aiAnalysis` ∈ `Available | Processing | Incomplete | Not started`; `policyMatch` ∈ `Matched | Partial | Requires Review | Not Evaluated` (display-style values, sent as-is).
- `updatedLabel` (`"Just now"`, `"12 min ago"`) is display text; `updatedMinutes` is the sortable number. The server should send both, or the frontend derives the label — see open questions.
- `photos[].url` points at stored files when uploads are real; today it is an in-memory object URL that dies with the tab.

### GET `/api/claims/:id`

Response `200`: one Claim (shape above). Error `404` — the frontend maps it to the workspace's existing "Claim not found" panel.

### POST `/api/claims`

Create a claim. Server must reproduce these rules (they live in `src/api/claims.js` today):

- `status` starts as `new`, `aiAnalysis` as `Not started`, `policyMatch` as `Not Evaluated`.
- `evidence` is `Complete` **only when all three document slots were filled** (≥ 3 documents); otherwise `Incomplete`.
- `evidenceItems` = photos + documents attached.
- `policyRef` empty → `"Not assigned"`; `incident` empty → `other`.
- New ids follow `CLM-#####` (next free number above the current max).

Request (what the modal hands over):

```json
{
  "customer": "Priya Nair",
  "date": "2026-10-08",
  "incident": "side_collision",
  "description": "T-boned turning left; airbags deployed.",
  "policyRef": "POL-90012",
  "priority": "high",
  "photos": [{ "name": "door-panel.jpg", "url": "blob:…", "caption": "Driver door" }],
  "documents": ["Accident report", "Policy document"]
}
```

Response `201`: the created Claim with `status: "new"` and `updatedLabel: "Just now"`.

Note: photo/document **bytes** are uploaded first (see the evidence endpoint); the create payload carries references (names/URLs) only. The mock treats `documents` as display names of filled slots.

### POST `/api/claims/:claimId/evidence`

Upload one evidence file.

- Request: `multipart/form-data`, field name **`file`**. No JSON body.
- Response `200`:

```json
{ "id": "evd-4021", "name": "front-bumper.jpg", "url": "/uploads/CLM-10482/front-bumper.jpg", "size": 1834011 }
```

Progress: the frontend's `(file, onProgress) => Promise<void>` seam expects upload progress; with `fetch` there is none, so use `XMLHttpRequest` `upload.onprogress` (or a streaming fetch) in `uploadEvidence`'s body. `onProgress` receives integers 0–100; 100 means done.

### Upload rules

Enforced client-side today (`src/pages/claims/CreateClaimModal.tsx` + `src/api/evidence.js`); **must also be enforced server-side**:

| Kind | Accepted types | Max size | Quantity |
| --- | --- | --- | --- |
| Photos | JPG (`image/jpeg`), PNG (`image/png`), HEIC (`image/heic`), WebP (`image/webp`) | **10 MB each** | **max 20 photos per claim** |
| Documents | PDF (`application/pdf`), DOCX (`application/vnd.openxmlformats-officedocument.wordprocessingml.document`) | **15 MB each** | 3 slots (accident report, customer statement, policy document) |

Violations → `413` (too large) or `422` (unsupported type), with a human-readable `message`.

### POST `/api/chat/messages`

Request:

```json
{ "question": "Summarize the evidence for this claim.", "claim_id": "CLM-10476" }
```

Response `200`: **one assistant `ChatMessage`** (the frontend appends it to the active conversation):

```json
{
  "id": "msg-003",
  "role": "assistant",
  "time": "09:41",
  "demo": true,
  "sections": [ /* Section[] */ ],
  "activity": [ { "text": "Checking policy coverage" } ]
}
```

- `claim_id` is optional (snake_case on the wire; the JS layer maps it from `{ question, claimId }`).
- `demo: true` marks canned content — keep it `true` only while responses are illustrative; drop it when a real model is behind this endpoint.
- Failure shape: standard error envelope; the chat UI renders `message` in a retryable error bubble.
- Streaming: **not simulated today** — see open questions. If streaming is chosen, keep this envelope as the non-streaming fallback (the UI would then consume SSE chunks that assemble into the same `ChatMessage`).

## Shared vocabulary

Defined once in `src/lib/constants.ts`; the API sends/receives **tokens**, and the frontend maps them to display text via label helpers (visible wording must not change).

**Stages** (`status`):

| Token | Label |
| --- | --- |
| `new` | New |
| `evidence_collection` | Evidence Collection |
| `ai_analysis` | AI Analysis |
| `human_review` | Human Review |
| `completed` | Completed |

**Priorities**: `high` → High, `medium` → Medium, `low` → Low.

**Incident types**: `rear_end_collision` → Rear-end Collision, `side_collision` → Side Collision, `vehicle_collision` → Vehicle Collision, `other` → Other.

Deep links use the same tokens (`#/claims?tab=human_review&incident=rear_end_collision&priority=high`), so route query params and API params must stay identical.

## Open questions for backend

1. **Auth method** — JWT (how long-lived? refresh rotation?) vs. server-side sessions? Where does the token live (localStorage is what `src/api/http.js` uses today — acceptable, or should it be an httpOnly cookie, which would make the bearer helpers unnecessary)? Also: is `POST /api/auth/login` the only entry, or do SSO/OIDC providers need to exist behind it?
2. **Chat streaming or not** — should `POST /api/chat/messages` stream tokens (SSE/WebSocket) so the reply renders progressively, or is a single buffered response acceptable? The UI currently waits ~750 ms and renders one complete message; streaming needs a new client path (the response envelope above would stay the final assembled shape).
3. **File storage** — where do evidence files live (S3/GCS bucket, local disk, object store)? Signed URLs with expiry for `photos[].url`? Virus scanning / image re-encoding on upload? Retention rules for claim evidence? Today the "upload" is simulated in-browser and `url` is a dead blob reference.
4. **Role permissions** — `user.role` exists (`claims_reviewer`) but nothing is gated. Which roles are planned (reviewer, approver, admin, read-only)? Which endpoints/fields become role-dependent (e.g. who may move a claim to `completed`, who sees customer PII)? Should unauthorized access return 403 with a `forbidden` code the UI can message?

Additional smaller items:

5. Should the server send `updatedLabel`/`dateReported` display strings (the mock does), or only `updatedMinutes`/`dateReportedValue` with the frontend formatting? Deriving client-side is cleaner but shifts format decisions to the frontend.
6. Are filters on `GET /api/claims` applied server-side with stable sorting across pages (needed once pagination turns on), and is there a maximum `page_size`?
7. Timezone policy for `dateReportedValue` (contract assumes UTC midnight) and is the "Today/Yesterday/Just now" relative labeling the server's job or the client's?
